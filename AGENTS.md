# Общие правила для AI-разработки сервисов

Этот файл — **универсальные инструкции для любого прикладного репозитория**. Он не описывает бизнес-логику конкретного сервиса. Проектные решения, API, TTL, форматы данных, порты, UI и ограничения определяются ТЗ и локальными документами проекта.

**Приоритет:** явное решение владельца → проверенный текущий код и проектные контракты → актуальные правила `Amadu-A/shared_infrasktructure/docs` → этот файл → defaults библиотек. При противоречии не принимать решение молча; указать конфликт и запросить решение владельца.

## 1. Обязательная проверка перед работой

1. Установить фактические `git remote -v`, `git status --short`, текущую ветку и `git rev-parse HEAD`; сравнить локальный код с соответствующей веткой на GitHub. Не ориентироваться на старую переписку или ранее выданный код как на актуальный репозиторий.
2. Прочитать **полностью** затрагиваемые файлы, контракты, тесты, миграции и конфигурацию. Прежде чем исправлять ошибку, сопоставить последнюю рекомендацию с командами/логами пользователя, выделить расхождения и определить источник ошибки.
3. Сначала изучить актуальный `https://github.com/Amadu-A/shared_infrasktructure/blob/main/docs/LLM_CONTEXT.md`, затем по типу задачи: `ENGINEERING_GUIDELINES.md` (backend), `FRONTEND_GUIDELINES.md` (UI), `INFRASTRUCTURE_INSTRUCTIONS.md` (Docker/deploy/shared). Если подключается shared-сервис — также `docs/services.yaml`. Эти файлы — **source of truth**; пути и контракты проверять заново, не копировать по памяти.
4. Сверить локальные `AGENTS.md`, `README.md`, `pyproject.toml`, `compose.yaml`, `.env.example`, `ops/`, `scripts/`, `tests/` и относящиеся к задаче `docs/`. При наличии готового скрипта/модуля дорабатывать его, а не создавать дубль.
5. Выполнять только согласованный этап. Не перестраивать существующую архитектуру и не внедрять новые фреймворки, очереди, базы, модели или UI без причины. Не выдавать план, mock или успешный unit-test за проверенную эксплуатацию.

## 2. Код, архитектура, документация

- Соблюдать PEP 8, type hints, Ruff, небольшие функции, DI и границы `domain → application/ports ← infrastructure`, отдельно `presentation`, `workers` и composition root в той степени, в какой это оправдано проектом. Домен не зависит от HTTP, SQLAlchemy, RabbitMQ или UI; SQL только в слое доступа к данным; один use-case для web/API/CLI.
- Следовать фактическим проектным паттернам. Предпочитать минимальные изменения; не создавать «архитектуру на будущее» и параллельные реализации одной операции. Идемпотентность, явные ошибки, ограниченные retry/timeout, транзакции и сохранение исходных данных обязательны там, где могут быть повторы и сбои.
- Комментарии, docstrings, README и проектную документацию писать **на русском языке**. Для новых/изменённых файлов указывать относительный путь; первая допустимая строка комментария — путь файла согласно `ENGINEERING_GUIDELINES.md`. Исключения — обязательные shebang/служебные заголовки.
- Для frontend соблюдать `FRONTEND_GUIDELINES.md`: семантический HTML, доступность, разделение JS/CSS, отсутствие inline-обработчиков, безопасный вывод пользовательского текста. Не превращать UI в набор декоративных виджетов, если ТЗ требует рабочую таблицу.
- Не хардкодить адреса серверов, физические имена AI-моделей, GPU, порты, пароли или токены. Если используется модель, указывать её логический контракт, а не размещение на конкретной видеокарте.

## 3. Конфигурация и секреты: `.env.example` / `.env`

- В `.env.example` (в Git) описывать **все поддерживаемые переменные**: безопасные значения по умолчанию, имена хостов, порты, feature flags, limits/timeouts и пустые/фиктивные placeholders для секретов.
- В `.env` (в `.gitignore`, права доступа ограничены) хранить **реальные пароли, ключи, токены** и только необходимые частные переопределения окружения. Не копировать весь `.env.example` в `.env`, не перетирать действующий `.env` при деплое и не хранить настоящие секреты в `AGENTS.md`, README, Git, тестовых отчётах или логах.
- Для Python использовать `pydantic-settings` / `BaseSettings` с layered `env_file=(".env.example", ".env")`. Порядок: безопасный baseline → приватный override → переменные процесса. Проверять обязательные значения до старта приложения.
- Docker Compose **не наследует автоматически** этот порядок Pydantic. Предусмотреть согласованный способ применения defaults/overrides в `up.sh`, тестах, CI, `docker compose config` и runtime: defaults в Compose через `${VAR:-default}` либо единый явный layered loader. Секреты — обязательные `${VAR:?error}`, без небезопасного fallback. Проверять реальную интерполяцию без раскрытия secret values.
- Порт, URL, TLS, имя контейнера, CPU/RAM limit, batch size и частота обхода — не секреты; не заставлять пользователя добавлять их в приватный `.env`, если годятся утверждённые defaults. Но фактический внешний host/port согласовывать с сервером.
- `.gitignore` обязательно исключает `.env`, локальные ключи, `.log`, кэши, временные файлы и **`examples/`**. Если `examples/` уже tracked, не удалять файлы из Git без разрешения владельца; сообщить, что `.gitignore` не отменяет прежнее отслеживание. Постоянные синтетические фикстуры для CI держать в `tests/fixtures/`.

## 4. Shared infrastructure — не создавать и не перезапускать чужие сервисы

Единый источник контрактов — `Amadu-A/shared_infrasktructure/docs/services.yaml`. На одном Docker host при наличии разрешения подключать нужные контейнеры к external network `ai-shared`. БД, очереди рабочих задач, файлы и volumes конкретного проекта изолировать в его собственных ресурсах и private network.

| Общий сервис | Docker endpoint / условие |
| --- | --- |
| VLM | `http://shared-vlm:8000/v1`, модель `shared-vlm` |
| Embedding | `http://shared-embedding:8000/v1`, модель `shared-embedding` |
| RabbitMQ | `rabbitmq:5672`, свой application user и vhost |
| Docling Serve evaluation | `http://docling-eval:5001`, отдельный API key, см. §6 |
| SearXNG | `http://searxng:8080`, только если включён optional profile |
| n8n | `http://n8n:5678`, только для обоснованных внешних workflow |

Эти значения — **внутренние логические контракты**, а не доказательство того, что контейнеры сейчас запущены. На другом host использовать согласованные опубликованные endpoints и правила firewall/VPN. Не использовать `localhost` для обращения из одного контейнера в другой.

Запрещено: поднимать собственный RabbitMQ/LLM/Docling «для удобства», использовать `n8n-db` как БД приложения, применять shared admin credentials в runtime, без разрешения делать `restart`, `recreate`, `down`, `prune`, менять GPU/model/TP/DP, сети, volume или `.env` shared-инфраструктуры. PostgreSQL/Qdrant — **project-specific** по умолчанию. Зависимости должны иметь timeout, bounded retries, readiness и диагностируемую деградацию.

## 5. RabbitMQ: безопасное создание project user и vhost

**Обязательное правило:** существующие `shared_admin`, `shared-admin`, bootstrap-admin и любые другие чужие учётные записи неприкосновенны. Различать имена буквально; нельзя угадывать, какой из них главный. **Никогда** не выполнять для них `delete_user`, `change_password`, `clear_password`, `set_user_tags`, `set_permissions` или восстановление definitions. Не менять `RABBITMQ_DEFAULT_USER`, `RABBITMQ_DEFAULT_PASS`, `RABBITMQ_REQUIRED_VHOSTS` и общий compose. Не использовать администратора в connection string приложения.

Для каждого проекта выбрать **уникальные** `RABBITMQ_USER`, `RABBITMQ_VHOST`, `RABBITMQ_PASSWORD`; username и vhost привязать к slug проекта. Пароль сгенерировать безопасно один раз и хранить в закрытом проектном `.env`; повторный `up.sh` не должен генерировать новый пароль или сбрасывать существующий.

Порядок bootstrap на Docker host:

1. Проверить по `docker ps` имя **реального** контейнера RabbitMQ, его работоспособность и доступность. Если нет доступа к Docker или к брокеру — остановить provisioning и запросить у владельца вывод диагностики.
2. Прочитать список существующих пользователей и vhost командой `rabbitmqctl list_users` / `list_vhosts` **без изменений**.
3. Проверить, что создаваемый username не совпадает с любым admin, а vhost не принадлежит другому проекту. При конфликте остановиться, не изменять чужой ресурс.
4. Создать **только отсутствующие** project user/vhost. Пароль передавать через stdin (не в аргументе команды и не в логах). Для существующего пользователя **не выполнять reset/rotation** автоматически. Если сохранённый пароль не подходит, остановиться и сообщить владельцу.
5. Назначить обычному project user права только на его собственный vhost: `configure`, `write`, `read`. Не выдавать теги `administrator`, не предоставлять права на `/` или чужие vhost.
6. Проверить `list_permissions -p <project-vhost>`, затем реальное AMQP-подключение **под project user** и создание/чтение тестового сообщения в project namespace. Удалять только собственные тестовые ресурсы.
7. При повторном `bash scripts/up.sh` пользователь, vhost, пароль, права и существующие очереди должны сохраняться. Не рестартовать RabbitMQ для создания учётной записи.

**Проверяемый операторский пример (на сервере; заменить три переменные на проектные значения, имя контейнера взять из `docker ps`):**

```bash
RABBIT_CONTAINER='ИМЯ_ДЕЙСТВУЮЩЕГО_КОНТЕЙНЕРА'
APP_RABBIT_USER='my_project_app'
APP_VHOST='my-project'

# Проверить доступность брокера и только затем читать состояние:
docker exec "$RABBIT_CONTAINER" rabbitmqctl ping || { echo 'RabbitMQ unavailable'; exit 1; }
KNOWN_USERS="$(docker exec "$RABBIT_CONTAINER" rabbitmqctl list_users -q)" || exit 1
KNOWN_VHOSTS="$(docker exec "$RABBIT_CONTAINER" rabbitmqctl list_vhosts -q)" || exit 1
printf '%s\n' "$KNOWN_USERS"
printf '%s\n' "$KNOWN_VHOSTS"

# Жёсткая защита от изменения администраторов:
case "$APP_RABBIT_USER" in
  shared_admin|shared-admin|guest|administrator) echo 'Forbidden user'; exit 1 ;;
esac

# Создаём vhost, только если его ещё нет:
if ! printf '%s\n' "$KNOWN_VHOSTS" | grep -Fxq -- "$APP_VHOST"; then
  docker exec "$RABBIT_CONTAINER" rabbitmqctl add_vhost "$APP_VHOST"
fi

# Новый пароль вводится без эха; при существующем user не сбрасывается:
if ! printf '%s\n' "$KNOWN_USERS" | awk '{print $1}' | grep -Fxq -- "$APP_RABBIT_USER"; then
  read -rsp 'Пароль НОВОГО project RabbitMQ user: ' APP_RABBIT_PASSWORD
  printf '\n'
  test -n "$APP_RABBIT_PASSWORD" || { echo 'Empty password forbidden'; exit 1; }
  printf '%s\n' "$APP_RABBIT_PASSWORD" | docker exec -i "$RABBIT_CONTAINER" rabbitmqctl add_user "$APP_RABBIT_USER"
  unset APP_RABBIT_PASSWORD
fi

# Выдаём права ТОЛЬКО в собственном vhost после проверки его ownership:
docker exec "$RABBIT_CONTAINER" rabbitmqctl set_permissions -p "$APP_VHOST" "$APP_RABBIT_USER" '.*' '.*' '.*'
docker exec "$RABBIT_CONTAINER" rabbitmqctl list_permissions -p "$APP_VHOST"
```

Пример предназначен для **уполномоченного оператора** и выполнения как отдельного shell-скрипта; `exit` прерывает его при ошибке. **Перед `set_permissions` оператор обязан подтвердить, что vhost действительно принадлежит проекту**. В настоящем `up.sh` проверка ownership/config проекта обязательна до любых write-операций; нельзя путать отсутствие ресурса со сбоем связи с RabbitMQ. Секрет, введённый при создании пользователя, должен совпадать с паролем в закрытом проектном `.env`; не выводить его на экран и не хранить в истории shell. Не запускать этот пример целиком без подстановки переменных и проверки контекста. Команды основаны на официальном RabbitMQ access-control/virtual-hosts API. Если проекту RabbitMQ не нужен, не создавать ни user, ни vhost.

## 6. Docling и OCR — только если нужны проекту

- Текущий shared contract: отдельный CPU-only evaluation service `docling-eval` в сети `ai-shared`; `http://docling-eval:5001`; с Docker host — `127.0.0.1:5001`. Авторизация через `DOCLING_API_KEY`; конкретный HTTP header/endpoint проверить по действующему API, не угадывать.
- Это **стенд оценки**, а не автоматически гарантированный production OCR-сервис. До включения в нагрузку проверить живой health, версию, payload, поддержку PDF/DOCX/изображений, OCR языков, лимиты CPU/RAM и доступную пропускную способность. `services.yaml` описывает ожидаемые лимиты, но не фактическую runtime-нагрузку.
- Не поднимать второй Docling и не менять shared `docling-eval` без отдельного разрешения. Не передавать `DOCLING_API_KEY` в browser/JS, логи, URL или Git; не копировать чужой секрет из shared `.env`.
- PDF и прочие документы обрабатывать через bounded concurrency, очередь и таймауты; не отправлять тысячи страниц одновременными запросами. Учитывать, что OCR — дорогая CPU-операция и другие проекты используют тот же endpoint. Backpressure/429/timeout показывать как состояние задачи, а не как молчаливый успех.
- Выбирать pipeline по потребности: текстовый PDF сначала извлекать нативно; Docling/OCR применять при необходимости для сканов, таблиц и сложной верстки. Не делать повторный OCR уже нормализованных страниц без явного требования.
- Перезапуск Docling и изменение его модели/параллелизма — операция владельца shared infrastructure, не side effect `scripts/up.sh` бизнес-проекта. Если текущий стенд не подходит по throughput, предоставить замеры и варианты, запросить отдельное решение.

## 7. Порты, внешняя публикация и безопасность

- Если проекту нужен web/API, **сервис должен быть доступен согласованным внешним клиентам**, а не только внутри контейнера. Заранее определить внешний URL, bind IP, свободный host port или reverse proxy, DNS/TLS и firewall; проверить достижимость с клиентской машины после запуска.
- Если пользователь **не указал сервер, занятые/разрешённые порты или схему публикации**, **запросить фактический вывод с сервера**, прежде чем закреплять порт и делать deploy:

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
docker compose ls
sudo ss -lntp
```

- Не подбирать host port наугад, не занимать порт другого приложения и не менять чужие Compose-конфигурации. `docker ps` не показывает все не-Docker слушающие процессы, поэтому нужен также `ss`.
- Публиковать только frontend/reverse proxy/необходимый API. PostgreSQL, Redis, Qdrant, RabbitMQ Management, Docling и внутренние workers **не публиковать открыто**. Не переносить правила доступа LAN/VPN из shared-сервисов на общедоступный интернет без отдельного security review.
- Если ТЗ допускает публичное чтение каталога без логина, это **не означает** открытые публичные `POST/PUT/PATCH/DELETE`, запуск парсинга, админку или чтение секретов. Административные операции защищать хотя бы VPN/IP allowlist/reverse proxy с отдельным операторским доступом; при требовании действительно публичных write-операций запросить архитектурное решение по авторизации и защите от злоупотреблений.
- Для внешнего HTTP-клиента/краулера ограничивать разрешённые schemes/hosts, запрет доступа к metadata/internal IP (SSRF), redirects, max response size/time, concurrency и retries. Соблюдать условия сайтов; не обходить CAPTCHA, блокировки и ограничения доступа.

## 8. Развёртывание и сохранность данных

- Для проекта предусмотреть **одну команду запуска**: `bash scripts/up.sh`. Она проверяет конфигурацию, необходимые ресурсы, сеть/порты, применяет только собственные миграции, запускает **только свои** контейнеры и проверяет readiness. Если инфраструктура уже есть — использовать её, не создавать новую.
- Повторный `up.sh` — идемпотентный. Не удалять БД, volumes, очереди, индексы, ранее собранные данные; не перегенерировать секреты; не обнулять checkpoints. Запрещены неконтролируемые `docker compose down -v`, `docker system prune`, `git reset --hard`.
- Если нужны новая schema, миграции или reindex — предусмотреть отдельно проверку, backup/rollback и ясные условия применения. Запускаемые сервисы не должны зависеть от открытой вкладки браузера; долговременные задачи сохраняют status/checkpoints в БД.
- Общие Docker network/service не пересоздавать. Shared недоступен — приложение сообщает `not ready` и причину, не пытается само перезапускать инфраструктуру.
- Health: `/health/live` и `/health/ready` (или существующий проектный эквивалент). Проверять не только статус контейнера, но и фактический API и UI.

## 9. Тесты и команды качества

- Ключевой функционал покрывать unit, functional, regression, architecture, API/contract и integration tests по релевантности. Ошибка в production → регрессионный тест. Моки не выдавать за live integration. Проверить сохранение всех ранее проходивших тестов.
- Предусмотреть **одну Windows PowerShell-команду**: `./ops/check-quality.ps1` (Ruff/lint, tests, architecture, applicable frontend tests, `git diff --check`). **Одну Linux-команду тестирования**: `bash scripts/test.sh`. Не создавать альтернативные `check2`, `up-new`, `deploy-v2` при наличии рабочих.
- При внутренних прогонах допускается перенаправлять большие успешные логи в `.log`; выводить в ответ итог, failures, counts и пути файлов. При ошибке прочитать полный log. **Команды, выдаваемые владельцу для ручного тестирования и деплоя, по умолчанию показывают вывод в терминале**; не добавлять к ним скрывающее перенаправление без запроса.
- Если для настоящих integration/live тестов нужны доступы, сервер или credentials, не объявлять их выполненными; указать, что именно заблокировано и как воспроизвести после предоставления доступа.

## 10. Git и формат ответа владельцу

- **Никогда самостоятельно не выполнять `git commit`, `git push`, `force push`, `git reset --hard`, публикацию релиза и изменения shared инфраструктуры.** Не использовать `git add .`. Не удалять серверные несохранённые файлы и рабочие пользовательские данные.
- В каждом этапе представить: что изменено; полный перечень файлов с относительными путями; какие контракты/миграции затронуты; результаты реально выполненных тестов; известные ограничения; команды для владельца.
- **В одном ответе** дать владельцу три группы команд: (1) Windows PowerShell — `./ops/check-quality.ps1`, просмотр diff, явный `git add <path> ...`, затем `git commit`/`git push` **только для исполнения владельцем**; (2) Linux — `git pull`, `bash scripts/up.sh`, `bash scripts/test.sh`, runtime health и необходимые миграции; (3) ручная проверка в UI/API — точный URL, что открыть, что должно быть видно, позитивный и негативный сценарии.
