# Этап 02.4. Автоматическая классификация

База реализации — `main` `6d3c3ef4461c3b5da7144914d4da92cdccdbcc4a`.
На aistation подтверждены та же версия, миграция `0003_catalog_pipeline`,
2540 категорий, 9 корней и прежняя контрольная сумма списка UUID.

Валидный `selected` автоматически назначает категорию после транзакционной
проверки актуального пути, существования UUID, активности предков, is_assignable
и статуса. Пригодная широкая категория также принимается. В SQL остаются способ,
источник решения, evidence и версия модели. Ручные решения и уже установленные
связи Product учитываются до нового выбора. Связь с категорией и установление
идентичности Product остаются отдельными действиями.

Вариант C использует Qdrant dense, PostgreSQL lexical и RRF, затем выполняет
ограниченный обход PostgreSQL при отсутствии подходящего выбора. У обхода
есть отдельные `answer_3` и schema, один возврат к родительскому уровню
и бюджет `CLASSIFICATION_VLM_BUDGET=10` на позицию. Три стратегии сравнения
используют те же реализации. Политика 02.4 использует существующую схему 0003.

## Диагностика ответов

Артефакт прежнего live-пилота содержит 46 строк с `invalid_output`.
Первый проход сохранил 198 `missing_unit`, 2 `invalid_unit` и 6 `invalid_price`.
В прежнем артефакте подробности ошибок модели отсутствуют. Из них нельзя
восстановить распределение по причинам или finish_reason. Рабочая БД при проверке
26 ноября не содержала заданий импорта этого пилота, который шёл в отдельной БД.

Новый аудит различает JSON, нарушение схемы, обрыв, UUID, evidence,
противоречивый статус и прочий технический отказ. Хранит этап, исходный ответ
и finish_reason, включая первую попытку при успешном исправлении. Для плохого
answer_1 явно написанный тип допускает отдельный режим `raw_name`. Он сохраняет
исходное имя и не подставляет неизвестные характеристики.

В живых ответах обнаружено сочетание `needs_review` с `broader`,
а также обрывы генерации. Оригинальные ответы сохраняются для проверки.
Обход назначил почкообразному медицинскому лотку кабельную ветку. Для этого
вида ошибок введена проверка конфликта назначения по исходному имени и пути.
Сопоставление сделано с данными Росздравнадзора независимо от предварительной
разметки. [Карточка Росздравнадзора](https://elk.roszdravnadzor.gov.ru/widget/med-product/136017)

## Сравнение A/B/C

Команда для отдельного стенда aistation:

```bash
bash scripts/test.sh --classification-live
```

Используются исходный AITIM-200, fixture из 2540 категорий, собственные временные
PostgreSQL/Qdrant и настоящие shared VLM/embedding. A — гибридный выбор,
B — последовательный обход, C — их сочетание. Порядок измерения A/B/C
циклически меняется между строками. Валидный answer_1 общий для одной строки,
его вызовы и время включаются в показатели каждой политики. Отдельно считаются
chat-запросы, сумма задержек строк, общая длительность стенда, доля назначений
и строки с техническими попытками. Повторы HTTP и исправления входят в число
chat-запросов. Запросы embedding учитываются во времени, но не в счётчике VLM.

Строчная выгрузка сохраняется постепенно в
`.tmp/reports/classification-aitim200.jsonl`. Финальные агрегаты сохраняются
в `.tmp/reports/classification-aitim200.json`.
При наличии независимо проверенной разметки используйте
`examples/aitim_200_gold.json` формата `{"1": ["uuid"], "2": []}`.
Ключ — номер строки, массив содержит допустимые UUID. Пустой массив означает,
что подходящей категории нет. Ключи для непроверенных строк отсутствуют.
`precision` и `recall` считаются только по строкам из Gold.

«Правильная категория» и «Комментарий пользователя» оставлены для проверки.

## Повторная классификация

`reclassify --job-id UUID` выводит предварительный отбор, а `--apply` ставит
задание в существующую очередь. Принимаются завершённые задания. Прежние ручные
назначения и исключения пропускаются, обработка читает сохранённые SQL-записи.
Оператор может вручную изменить автоматически назначенную категорию в UI.
